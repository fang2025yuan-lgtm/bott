# Bug fixes, QR check-in hardening, and Super Admin CRUD for UFQ EventBot (v2)

All six confirmed/likely issues from the v1 review have been addressed. `update_event_field` now gates writes through an `ALLOWED_EVENT_FIELDS` set. Deep-link parsing uses `split("_", 3)` with maxsplit to preserve underscores in the hash tail. `create_ticket` saves user and event data to local variables before the retry loop, eliminating the expired-object risk after rollback. No other blocking concerns remain.

**Verdict**: APPROVED

## High-level view

The sibling function `update_event(**kwargs)` retains the open `hasattr`-gated `setattr` pattern that was fixed in `update_event_field`. All three call sites today pass literal keyword arguments (`title=`, `registration_points=`, `status=`), never user-supplied keys. The risk only materializes if a future handler passes untrusted kwargs directly — adding `ALLOWED_EVENT_FIELDS` filtering would align it with the already-fixed function.

## `update_event` open-kwargs pattern

```python
async def update_event(event_id: int, **kwargs):
    async with AsyncSessionLocal() as session:
        event = await session.get(Event, event_id)
        if not event:
            return False, "Tadbir topilmadi"
        for key, value in kwargs.items():
            if hasattr(event, key):
                setattr(event, key, value)
        await session.commit()
```

No user-supplied string reaches `kwargs` keys. The concern is architectural: if a future handler does `await update_event(event_id, **user_data)`, it would write to `id`, `created_by`, or relationship attributes without rejection. Adding `if key not in ALLOWED_EVENT_FIELDS: continue` would align it with the already-fixed `update_event_field` pattern.
